# Localization (i18n) developer notes

This is a developer-facing reference for how translations actually work in
`optimize_images_x`, and the pitfalls that have already bitten this codebase
once. For the day-to-day task of adding a new language or updating an
existing translation, see **"Adding a new language"** in `README.md` — it has
the exact, tested commands. This document doesn't repeat those steps; it
covers the underlying implementation instead.

## How it fits together

- Domain: `optimize_images_x`. Catalogs live under
  `optimize_images_x/locale/<lang>/LC_MESSAGES/`:
  ```
  optimize_images_x/locale/
  ├── optimize_images_x.pot            # template, regenerated by extract_messages (gitignored)
  └── pt/LC_MESSAGES/
      ├── optimize_images_x.po         # translation source, committed
      └── optimize_images_x.mo         # compiled binary, gitignored — generated from the .po
  ```
- `setup.cfg`'s `[compile_catalog]`/`[extract_messages]` sections configure
  the domain, output paths, and catalog metadata for the `python setup.py
  extract_messages` / `compile_catalog` commands.
- Babel is declared as a build-time-only requirement (`pyproject.toml`'s
  `[build-system] requires`) and as a `dev` extra in `setup.py`
  (`pip install -e .[dev]`) — it's never a runtime dependency for end users,
  since nothing in the app imports it.
- `setup.py`'s `CustomSdist` command runs `compile_catalog` automatically
  before building an sdist, so a PyPI release always ships fresh `.mo`
  files. This does *not* run for a plain `pip install .` (wheel build) or for
  the PyInstaller build in `build.sh` — those need an already-compiled `.mo`
  on disk, produced by a prior manual `compile_catalog` run (or
  `./update-translations.sh`).

## Runtime language switching (`i18n.py`)

- `i18n._` and `i18n.ngettext_func` are module-level names holding the
  current translation functions. `i18n.change_language(lang_code)`
  reassigns them — for `'en'` (or an unavailable language), it swaps in
  identity functions instead of a real `gettext.translation`, since English
  is the source language and needs no `.mo`.
- Every module that needs translated text does `import optimize_images_x.i18n
  as i18n` and calls `i18n._(...)` — never `from optimize_images_x.i18n
  import _`, which would bind the function *reference* at import time and
  stop following later reassignment by `change_language()`.
- `i18n.LOCALE_DIR` checks `sys._MEIPASS` before falling back to
  `os.path.dirname(os.path.abspath(__file__))`, so it resolves correctly
  both running from source and inside a PyInstaller bundle (`__file__`-based
  paths land inside the frozen PYZ archive, not next to the bundled data
  files).
- `App.__init__` and `SettingsWindow.__init__` both call
  `i18n.change_language(app_settings.language)` on construction, to make
  sure the persisted setting always wins over whatever `gettext` guessed
  from the OS locale (Python's `gettext.translation()` falls back to the
  `LANG`/`LC_ALL` environment variables when no `languages=` is given, which
  is *not* the same thing as the user's chosen language, and would go stale
  the moment either of these constructors run).

## Marking new strings for translation

Wrap every new user-facing string in `i18n._(...)`, with the string as a
**literal argument**:

```python
# Good
label = ttk.Label(text=i18n._("Optimized images"))

# Bad — Babel's extractor only detects a literal string argument; a variable
# is invisible to it, and the string will never make it into the .pot no
# matter how many times you run extract_messages.
label = ttk.Label(text=i18n._(some_variable))
```

This is not a hypothetical: `gui/base_app.py`'s grid column headers and
`global_setup.py`'s `APP_NAME()`/`APP_LICENSE()`/`CREDITS()` were both
written as `i18n._(key)` over a dict/list of strings, and the translated
column headers and the entire About/Thanks window credits text silently
never got extracted — they just always rendered in English, with no error
or warning anywhere. Both had to be rewritten as one `i18n._("...")` call
per literal string.

For counts, use `i18n.ngettext_func(singular, plural, n) % n`. For strings
with placeholders, keep the placeholder inside the translated string (e.g.
`i18n._("{} of {}").format(a, b)`, not string concatenation), so a
translator can reorder the parts for their language's grammar.

## Pitfalls specific to this codebase

These have each caused a real, reported bug here — not generic gettext
advice:

1. **Indirect `i18n._()` calls are invisible to `extract_messages`.** See
   above. If a string looks correctly wrapped in `i18n._()` but never shows
   up in the `.po` after re-extracting, this is almost always why — check
   whether the argument is a literal or a variable.

2. **Module-level `i18n._()` calls are evaluated once, at import time**, and
   never update afterwards. `image_info.py`'s EXIF section titles
   (`{'image': 'Image', 'camera': 'Camera', 'gps': 'GPS'}`) used to be a
   module-level dict built with `i18n._(...)` values; it had to become a
   function (`_exif_section_titles()`), called fresh each time
   `read_image_info()` runs, so it reflects the language active *at that
   moment* rather than whatever was active on first import.

3. **A hardcoded string is easy to miss entirely**, especially window
   titles set once in `__init__` — `SettingsWindow` shipped with
   `self.master.title("Preferences")` (should've been
   `i18n._('Settings')`), and `ThanksWindow` with a bare
   `self.thanksRoot.title("Special thanks")`. Neither raised an error; they
   just silently never translated. When adding a new window, double-check
   every literal string passed to a widget constructor, not just the ones
   that look like body text.

4. **A window left open across a language change won't refresh unless it's
   both trackable and told to.** `AboutWindow`/`ThanksWindow` used to be
   thrown away on each open (`command=lambda: AboutWindow(...)`), so there
   was nothing to call back into when the language changed elsewhere.
   Fixing this needed two things together: (a) `main_window.py` tracking
   the open instance (`self.about_window`, checked with `winfo_exists()`
   rather than relying on a destroy callback, since the window can also be
   closed via a raw `<Command-w>` binding that bypasses
   `WM_DELETE_WINDOW`), and (b) a `refresh_language()` method on the window
   itself, called from `App.refresh_language()`. Any new persistent
   secondary window needs both parts, not just one.

5. **Translated text is usually longer than the English source**, and a
   fixed pixel width or window size tuned for English will clip it. This hit
   both the main window's grid columns (`original_size`/`new_size`/
   `percent_saved`, e.g. "Tamanho Original" vs "Original Size") and the
   Preferences window (whole tabs got clipped in Portuguese). For the
   Preferences window specifically, `SettingsWindow._min_content_width()`
   now measures the widest tab once (across all tabs, not just the current
   one) and `_resize_to_fit_current_tab()` never shrinks below it — plain
   per-tab `winfo_reqwidth()` isn't enough, because the language selector
   lives on the same tab you're already on when you change languages, so a
   resize keyed only to "the tab you just switched to" never fires for that
   specific change.

6. **`msgmerge` can silently produce a wrong or empty translation**, not
   just a `fuzzy`-flagged one — it once fuzzy-matched an unrelated existing
   string as if it were a close match, and separately dropped a translated
   multi-line entry back to empty on a later merge, with no warning either
   time. After running `./update-translations.sh`, check the translated
   percentage `compile_catalog` reports and skim `git diff` on the `.po`
   before trusting it — don't assume 100% just because nothing errored.

## Tooling

- **Poedit** (https://poedit.net) — GUI editor for `.po` files.
- **`msginit`/`msgmerge`/`msgfmt`** — GNU gettext command-line tools used by
  `./update-translations.sh` and the steps in `README.md`.
